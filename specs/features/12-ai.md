# Feature 12: AI

## Overview

The assistant, specified in full in `06-ai.md`. This document holds the behaviour that has to be tested.

Covers B2, B3, K8, A13.

## Behaviour

### Phone order form, route `/orders/new`

A form for a counter order plus an assistant panel. The barista pastes what the customer said, and `FormAIController` fills the form. Field rules, marker content, source tracking and confidence are as specified in `06-ai.md`.

### Order board assistant

A panel beside the board, at `/orders/ask`, that answers a question by filling a grid of its own from a query. `GridAIController` owns the grid it fills, so the board keeps its columns, its sorting and its selection, and the answer arrives next to it with whatever columns the question turned out to need. Questions it must answer in the demo: which orders are at risk of being late, which customer ordered the most this week, which orders have allergen comments.

### Dashboard assistant

A question turns into a chart through `ChartAIController`, in a fifth chart below the four fixed panels. The four answer what a bakery asks every morning; this one answers the question nobody wrote a panel for.

### What the assistant may query

Both controllers work by letting the model write SQL, which is a different kind of trust from letting it fill a text field, and the answer is not a sentence in a prompt. `BakeryDatabase` exposes three read-only views, `ai_orders`, `ai_order_lines` and `ai_products`, holding what a question about orders, products and revenue needs and nothing else: no tracking token, no password hash, no internal note, no address, no telephone number, no attachment. On top of that it accepts one statement, that statement a `SELECT` over those three names, capped at 500 rows and timed out at five seconds. A query that succeeds completely still cannot read anything private.

A database user with select only grants is the version that does not depend on that class being right. It needs a second data source and a different story on H2 and on PostgreSQL, and it is the first thing to add if this ever faces anything but a demo.

### Policy and meter

`RequestInterceptor` masks card shaped strings, rejects off topic prompts with a readable sentence, and postpones over budget prompts by dropping the oldest history. `ResponseMetadata` feeds a small panel with tokens, estimated cost and finish reason. A `max_tokens` finish tells the user the answer was cut off.

### Providers

One provider, the real one, under the `ai` profile with a key present. Without it the assistant is off and says so: a warning in the log and a red panel where the question box would have been. Nothing answers from a recording.

## Edge cases

| Scenario | Behaviour |
| --- | --- |
| The model proposes a product that does not exist | The write is rejected by the binder and reported back. The model corrects itself on the next turn |
| The model proposes a full slot | Rejected with the slot named, and the assistant proposes the next free one |
| The pasted text contains a card number | Masked before the request leaves, with a visible warning |
| The prompt asks about staff salaries | Rejected with a sentence, no request sent |
| A tool throws | `ToolException` gives the model a safe message, the stack trace stays in the log |
| The network dies mid demo | The turn fails and the panel says so. The form is still a form and the order can be saved by hand |
| No key, or no `ai` profile | Every assistant panel is red and says the assistant is off. Everything else on those screens works |

## Acceptance criteria

### AC1: Filling works and is honest
- [ ] Pasting the reference message fills name, phone, both product lines and the slot
- [ ] Every filled field carries a marker whose popover shows the source snippet and the confidence
- [ ] Editing a field clears its marker

### AC2: The model cannot break the rules
- [ ] It cannot write into a hidden field
- [ ] It cannot create a customer
- [ ] It cannot choose a product that does not exist or a quantity out of range
- [ ] It cannot book a full slot

### AC3: The policy layer holds
- [ ] A card shaped string is masked before the request
- [ ] An off topic prompt is rejected with a readable message and no request is sent

### AC4: The meter is accurate
- [ ] Every turn adds its token usage to the panel
- [ ] A truncated answer shows the cut off warning

### AC6: The live provider is real
- [ ] Built with `-Pai` and a key present, the application constructs a `SpringAILLMProvider` over the auto configured OpenAI model and says so on the about page and over the assistant panel
- [ ] The same build with no key boots, with the assistant off, rather than failing at startup
- [ ] Each orchestrator is handed a provider of its own
- [ ] Every test that needs a turn really calls OpenAI, and all of them are excluded from every default run by their tag

### AC5: It is honest when there is no model
- [ ] With no key the application boots, every view opens and nothing throws
- [ ] Every assistant panel shows a disabled state a person can see, and the startup log says why
- [ ] Asking for a session when there is none fails loudly rather than falling back
- [ ] With no model the form is still a form: a barista fills it by hand and a phone order lands
