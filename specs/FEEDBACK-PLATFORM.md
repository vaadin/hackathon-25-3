# Feedback for the Vaadin teams: not specific to 25.3

Findings that are older than this release. They were hit while building this application, but the behaviour is the same on 24.x and 25.0 to 25.2, so they belong to a different conversation than the 25.3 release notes.

Same rule as the other feedback file: one row per finding, and a row is a suspicion until somebody reproduces it.

**Where these went.** Four of them are drafted as issues in `specs/issues/`: the `AppLayout` shift is `03`, the download handler's missing session lock is `18`, and the four framework behaviours that are nobody's fault in particular are bundled as `45`. The rows that were our own notes rather than reports have moved into the specifications, where a reader of this application will find them: the JPA ones into `03-architecture.md` and the test ones into `08-testing.md`.

## Framework behaviour

| Finding | What happens | Why it matters | What we did |
| --- | --- | --- | --- |
| Navigating to the route you are already on does nothing | `ui.navigate(SameView.class)` is a no operation, so the view is not rebuilt and anything computed in its constructor keeps the old value | It cost us two debugging rounds: once when a locale switch appeared not to translate, once when a cart page appeared not to notice that a product had gone out of stock. In both cases the code was right and the test was wrong | Navigate away and back in tests, and bind anything that must react to a signal rather than computing it once in a constructor |
| `Grid` has no `bindItems` | Every other component got signal bindings. Grid did not, so the idiom is `Signal.effect(grid, () -> grid.setItems(...))` | It is the one place where the reactive story breaks and you drop back to imperative code, in the component people use most | Used the documented effect idiom. A `bindItems` taking a `Signal<List<T>>` or a `ListSignal<T>` would close the gap |
| `HasUrlParameter.setParameter` takes `BeforeEvent`, not `BeforeEnterEvent` | The interface is implemented with the wrong parameter type more often than not, and the compiler error names an abstract method rather than the mistake | Small, but it is a first ten minutes error for everyone | Nothing to do, worth a note in the javadoc |
| `AppLayout` paints its content at the full window width before reserving the drawer's space, and its own state says it is already settled | Load any route inside `AppLayout` cold, on a screen wide enough for an inline drawer, and sample the content's width every twenty milliseconds. Measured on `/kitchen` at a 1533 pixel viewport: at 169 ms the shell exists, the drawer is **already 256 pixels wide**, the side navigation is visible, the view is drawn and fully opaque, and the content is **1533** wide. At 190 ms the same content is **1277**. Nothing else changes in between: `drawer-opened` is true and `overlay` is absent in both samples, so both attributes hold their final values throughout the shift. An in app navigation to the same route has no shift at all, so it is the cold load only | Every cold load of an application built on `AppLayout` shifts all of its content sideways by the drawer's width, roughly twenty to fifty milliseconds after painting it. That is a visible jump rather than a hydration detail: the drawer, the navigation and the view are all on screen and opaque while the content is laid out as though the drawer were not there. The second half is worse for anyone automating: because the component's state is final before its geometry is, there is nothing to wait for. A layout test that measures on arrival measures the wrong frame, and waiting for `drawer-opened`, for the absence of `overlay`, or for two equal readings in a row all failed here, in four runs out of nine | Do not measure absolute widths against a value read earlier. Ours reads the content's width and its container's in one script call and compares the **share**, which is stable whatever the drawer is doing. What would fix it properly is reserving the drawer's space before the first paint of the content, and failing that, an attribute or event that says the layout has settled. Not verified against 24.x: `AppLayout` is old enough that this is probably not new | `KitchenSummaryOverlayIT.java`, `BrowserIT.java` |
| A CSS grid inside a `VerticalLayout` collapses to one column | `VerticalLayout` aligns its children to the start, so a child is as wide as its contents. A `display: grid` child with `repeat(auto-fit, minmax(20rem, 1fr))` therefore has one column's worth of width to fit into, and lays every panel out under the one before it | The rule reads as if it responds to the window and it responds to nothing. It looks like a broken media query, and it cost us the same half hour twice, on the dashboard and on the diagnostics view, before we recognised it the second time | `width: 100%` on the grid, every time. A `VerticalLayout` that stretched full width children by default, or a note in its documentation saying children do not stretch, would stop this being a rite of passage |
| A `BeanValidationBinder` shows Hibernate Validator's English defaults, and nothing says so | Bind a bean with `@NotBlank` and validate. The field reads "must not be blank", in English, in every language the application offers, because the message comes from the validation implementation's own bundle and not from the Vaadin i18n provider | An application whose rule is that no user visible string is a literal still ships a screenful of them, and it is invisible until somebody submits an empty form in the second language. Ours reached a checkout step where four fields said it at once | Our own `ValidationMessages.properties` in three languages, which Hibernate Validator picks up by convention, plus a message key of its own on the telephone constraint so that a wrong number says what to type. It works, including the Spanish, and it took reading the Bean Validation specification rather than anything in the Vaadin binder documentation, which never mentions where a constraint message comes from |
| A `DownloadHandler` runs without the session lock, and nothing says so where you would look | The download pages show a callback that builds bytes and returns them, and reading UI state inside it is the obvious thing to do: ours read two signals to know what the filter showed. The locking is mentioned once, in a note under an unrelated example about updating the UI afterwards, as "`UI.access` is needed for updating the UI and also session locking if you want to access the session" | A read of UI state from an unlocked request is a race that will not show up in testing, because a test calls the callback on a thread that happens to hold the lock. And a callback that throws has no screen to fail on: the browser gets whatever the container makes of the exception and the person gets nothing, which reads as the application having crashed | Copy what the download needs into a snapshot written under the lock, and catch inside the callback so a failure becomes `DownloadResponse.error(500, message)` with the context in the log. A sentence on the `DownloadHandler` page saying the callback holds no lock, next to the code somebody is about to copy, would have saved the reasoning |

## Spring integration

| Finding | Detail | Suggestion |
| --- | --- | --- |
| `spring.jpa.defer-datasource-initialization=true` and `ddl-auto=validate` are silently incompatible | With deferral on, Hibernate validates before `schema.sql` runs, so the application fails to boot with "missing table". The Boot documentation recommends deferral for `data.sql`, and the Vaadin starters inherit that advice | A line in the Vaadin persistence documentation saying that an explicit schema plus `validate` means deferral must be off would prevent it |

## Tooling and ecosystem

| Finding | Detail |
| --- | --- |
| Service workers outlive the application they were built for | A `@PWA` service worker registered by an earlier build kept serving a cached shell after the routes changed, producing a redirect loop that looked like a security misconfiguration. Nothing in the dev tools suggested clearing it | In development, a way to disable or auto invalidate the service worker between restarts would save real time |
| The old Bakery starter is still the most visible example | It is deprecated in its own README, yet it is what people find. Every pattern in it, from Lit templates with `@Id` to display DTOs of preformatted strings, is now the wrong advice | Retiring it, or putting a modern rewrite next to it, would move the whole community forward faster than any single API |
