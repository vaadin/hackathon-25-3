# Feedback for the Vaadin teams: 25.3

Everything found while building this application on 25.3.0-beta1 that a Vaadin team could act on: an API that is missing, one that is awkward, one that is documented but absent, and every place where we had to write a workaround.

This file is part of the specifications on purpose. If this application is ever rebuilt from these specifications, whoever does it should hit none of this by surprise, and should check whether each entry is still true.

**How to add an entry.** One row per finding, in the table that matches its kind. Say what was expected, what happened, what we did instead, and where in this repository the workaround lives. If it is fixed later, do not delete the row: mark it fixed and in which version, because the code that works around it still has to be cleaned up.


## What happens to these

Nothing here has been posted. This file is the raw list, and the pipeline is `specs/issues/`, which holds a draft per finding and a small project per draft. **Start there:** its README says what is ready to post, what still needs cutting down, and what was withdrawn.

**One issue per finding**, in the repository that owns the thing rather than in this one. An API on the server, a binder, a signal, the router goes to `vaadin/flow`. How a component behaves in the browser goes to `vaadin/web-components`. Something documented that does not exist goes to `vaadin/docs`, naming the page. A version or BOM problem, or a case where nobody can tell which module owns it, goes to `vaadin/platform`.

An issue needs less prose than a row here and one thing a row does not always carry: **the smallest thing that reproduces it**. A finding whose reproduction is "this application, on this branch, on this screen" is not ready.

**What this file no longer holds.** Rows that turned out to be wrong are deleted rather than struck through, and the lesson from each is in `specs/issues/README.md`, which is where somebody deciding what to file will look. Rows that were our own rule rather than a report moved into the specifications: the testing ones into `08-testing.md`, the dev loop ones into `10-dev-loop.md`. The list of what worked exactly as advertised moved into `REPORT.md`, because that is where the hackathon's account of the release belongs.

Five findings have been withdrawn so far, and every one was killed by building the reproducer or repeating the steps. That is the point of this arrangement: a row is a suspicion, and a project is a fact.

**A hackathon report**, which is the other half. `REPORT.md` carries the numbers and what was built; this file carries what the platform got wrong. The report is written from both, at the end, and it is the only place where "we found fourteen things" is a useful sentence. Here, one row is one thing.

When an issue is opened, put its link at the end of that row. A finding with no link is a finding nobody outside this repository has seen.

## A lazy Grid cannot have a select all checkbox, and cannot be given one

Asked for: the select all checkbox the [Grid selection docs](https://vaadin.com/docs/latest/components/grid/selection#multi-select-mode) show, on a board whose rows come from `setItemsPageable`. For a paged grid, "select all" has an obvious and useful meaning, every row the current filter matches, which is what somebody scrolling the list thinks they are selecting. There is no way to build it in the header. Every door was tried and measured on this application, on 25.3.0-beta1.

| Door | What happens |
| --- | --- |
| `setSelectAllCheckboxVisibility(VISIBLE)` | Nothing. The enum documents it: VISIBLE "shows the select all checkbox, **if in-memory data is used**". DEFAULT is the same rule. With a lazy provider the checkbox stays hidden whatever you pass |
| The column's own switch | `GridSelectionColumn` is public, is the grid's first element child, and `setSelectAllCheckBoxVisibility(true)` on it **does** show the checkbox. Reachable as `grid.getElement().getChildren()` filtered to that type, and it has to be re-applied after every `setItems*` call because the model resets it |
| Clicking that checkbox | **Ticks, and selects nothing.** Zero rows selected, no error, no log line. The client sends `$server.selectAll()` and the model's callback is guarded for in-memory data, so the control lies: it looks selected and the selection is empty. This is worse than the checkbox being absent |
| Substituting the callbacks | `GridSelectionColumn(SerializableRunnable selectAll, SerializableRunnable deselectAll)` is a public constructor, which is exactly the hook needed, but the instance is created inside the selection model and there is no setter, no getter for the callbacks, and no "select all requested" event on `GridMultiSelectionModel`. `addClientItemToggleListener` covers single rows only |
| A header cell above the selection column | `grid.prependHeaderRow().getCells()` returns **8 cells for 8 data columns**, and the default header row the same: `rows=1 columns=7 cells=7`. No cell is created for the selection column in either. `HeaderRow` cells wrap `AbstractColumn`, and `GridSelectionColumn` extends `Component` rather than `AbstractColumn`, so it has no header API of its own and `getCell(Column)` cannot name it either. `HeaderCell.setComponent` cannot reach that header |
| A checkbox in the first data column's header | Possible, but that column is sortable and the grid wraps header content in `vaadin-grid-sorter`, so one click both ticks the box and re-sorts the board |

What is left is a client-side override of `_selectAll` on the custom element, which is not something an application should be writing.

**What we would want.** Either a `setSelectAllHandler(SerializableConsumer<Boolean>)` on `GridMultiSelectionModel`, or a "select all requested" event, so that an application can define select all for its own data. The pieces are already there: the column takes callbacks, and the enum already knows the difference between in-memory and lazy. A second best would be a header cell above the selection column, so an application can put its own control where a person looks for it.

**A correction to the row above, and it matters.** The "no cell above the selection column" finding is real and stands: `GridSelectionColumn` extends `Component` rather than `AbstractColumn`, confirmed with `javap` against the jar, so it carries no header API at all, and both the default header row and a prepended one have exactly one cell per data column and none for it. What was too strong was the conclusion drawn from it, that nothing can be reached in that cell. `grid.addContextMenu()` reaches the whole header, the select all cell included, and `GridContextMenu.setDynamicContentHandler` is handed a `null` item when the menu opens on the header rather than on a row, which is what makes "the header only" expressible:

```java
var menu = grid.addContextMenu();
menu.setDynamicContentHandler(item -> item == null);  // header, not rows
```

Verified with real right clicks rather than synthesised events, which carry no item context and open regardless: over the select all cell the menu opens, over a row it does not. So a persistent control cannot live in that cell, and a menu opened from it can. This repository's column chooser is now exactly that, in `ColumnChooser.onHeaderOf`.

**What this application does instead: nothing.** A filter-wide select all was built and then removed, deliberately. It worked, as a labelled checkbox in the board's toolbar that selected every order matching the current filter, through the same specification and sort the grid fetches with and capped at 500 with a notification when it capped. It was removed because a control that says "select all" while sitting outside the table, over a list that pages, and feeding bulk confirm and bulk cancel, is a control that will one day be trusted to mean something it does not. The board keeps per row checkboxes and the two bulk actions, and offers no select all at all. The capability stays unimplemented until the platform can express it where it belongs.

## Behaviour that surprised us

| Finding | What happens | Why it matters | What we did |
| --- | --- | --- | --- |
| A field's colspan cannot vary across responsive steps, so the two `FormLayout` modes each hold half of an ordinary responsive form | Wanted, on the storefront filter bar: four filters in one row when wide, the search across the top of the other three when medium, and one column with the labels beside their fields when narrow. Responsive steps mode gives per breakpoint column counts and per breakpoint label positions, but `setColspan` is one static number clamped to the active step's column count (`responsive-steps-layout.js`, `colspan = Math.min(colspan, columnCount)`). Effective span therefore cannot decrease as columns grow, so no static value is 3 of 3 at one step and 1 of 4 at another, and no per field assignment rescues it either: the wide state forces the search and the other filters equal, the medium state forces the search to be three times them. Auto responsive mode does expose the span as a CSS custom property, so a container query could vary it, but its own `labelsAside` means "aside whenever they fit", which puts labels beside the fields when the bar is **wide** and above them when narrow, the inverse of what a narrow phone layout wants, and the mode has no way to say "aside only in one state" | Nothing exotic was being asked for. Four filters that reflow to a phone is the most ordinary responsive form there is, and it needs exactly two things at once: a span that changes with the breakpoint, and labels that move aside only in the narrow state. Neither mode has both, and the private `--_grid-colspan` in the mode that has the first is not a public API | Chose column counts that divide the field count instead: four columns, two, then one, which four filters fill evenly, so no state strands a field and no colspan is needed anywhere. That is a real answer for four fields and no answer at all for three or five, where some state always leaves a remainder and the span that would absorb it cannot vary. Written into `03-storefront.md` so nobody re-adds a three column state and rediscovers the stranded row. The fix we would want is `ResponsiveStep` taking colspan overrides, or a public per item colspan custom property so a container query can do it |
| `setMaxColumns` is silently capped by what the content uses | In auto responsive mode, `setMaxColumns(4)` with four fields added directly to the layout renders **one** column. The element property really is 4, and the component then writes `--_max-columns: Math.min(Math.max(minColumns, maxColumns), maxColumns)` where that last one is the widest row it finds in the content (`auto-responsive-layout.js:134`). With `autoRows` off, which is the default, every direct child resets the counter, so the widest row it can find is 1. `setAutoRows(true)`, or grouping fields with `addFormRow`, is what unlocks it | The javadoc for `setMaxColumns` says "Sets the maximum number of columns that the component can create" and says nothing about the content capping it, so the symptom is a four column layout rendering as one with every property set correctly. We only found it by reading the web component's source | Called `setAutoRows(true)`. Then moved to responsive steps mode for unrelated reasons, so the call is gone from this repository. Worth a sentence in the javadoc: `maxColumns` is an upper bound on what the content asks for, not a request for that many columns |

## A stylesheet added at runtime is not covered by the dev loop's CSS push

`apply` reported `hmr: 1 resource(s) copied, pushed 1 stylesheet(s) in place` for an edit to a stylesheet the application had added with `page.addStyleSheet` at runtime. The file on disk and the copy on the classpath were both new; the browser kept the old one, and the page went on rendering the previous rules.

It is a convincing failure because the report is green and the change is real everywhere except where it matters. We only caught it by reading the rule text back out of `document.styleSheets` and finding the old declaration still there. The confusion lasted a while because switching between a variant that loads the sheet and one that does not re-adds the link, which does fetch the new file, so the change appeared to work whenever a probe happened to switch themes on the way.

Either push the runtime added sheets too, or say `pushed 1 of 2` and name the one that was not pushed. A reload fixes it, but only if you know you need one.

## The container tokens are not interchangeable between themes

`--vaadin-background-container` and `--vaadin-background-container-strong` are in the shared layer, so an application reasonably writes `background: var(--vaadin-background-container)` and expects a sunken surface under either theme. They do not behave the same way:

| Theme | Value |
| --- | --- |
| Lumo | `light-dark(rgba(25,59,103,.05), ...)`, a fixed cold blue grey wash |
| Aura | `color-mix(... from the background colour ...)`, derived from whatever the background actually is |

On a warm background Aura's stays warm and Lumo's reads as a dirty grey white, so the same stylesheet looks deliberate in one theme and broken in the other. It is the one token pair we found where writing against the shared layer is not enough, and it took a side by side comparison to see: each looks plausible on its own.

Deriving Lumo's from `--vaadin-background-color` the way Aura does would make the shared layer mean the same thing in both.

## Missing pieces in the shared token layer

Both themes feed the same `--vaadin-*` properties, which is genuinely good: an application can be written against `--vaadin-background-color`, `--vaadin-text-color`, `--vaadin-border-color`, `--vaadin-radius-*`, `--vaadin-gap-*` and `--vaadin-padding-*` and it follows whichever theme is loaded. This application does exactly that and switching theme at runtime just works.

There is no name for a **raised surface**. `--vaadin-background-color` is the page and `--vaadin-background-container` is a sunken wash, so a card that should sit *above* the page has nothing to ask for. Every application that draws cards therefore invents its own token, and they will all invent a different one.

Setting `--vaadin-background-color` is also **not** how you set the page colour under Aura. Aura recomputes it from its own `--aura-background-color-*` properties rather than passing a value through, so an application that sets the shared token gets a colour three points away from the one the page actually paints. Invisible in isolation, and visible on a sticky bar that has to match the page it sits on. Under Lumo the same assignment lands exactly.

The other gap is the accent. There is no document level `--vaadin-` name for the theme's primary or accent colour: `--vaadin-focus-ring-color` exists only inside component scopes, and everything else is prefixed `--lumo-` or `--aura-`. So an application that wants to paint one of its own elements in "the theme's accent" has to know which theme is loaded, which is the one thing the token layer otherwise saves it from. We left our accent out of the plain variants rather than guess.

## Suggestions

0. Make the old dark mode pattern say something. Setting `theme="dark"` under Aura is a no operation, and it is what every existing example teaches.
1. Ship `bindChildren`, or remove it from the 25.3 documentation until it ships. Right now the first thing a reader tries does not compile.
2. Make `peek()` on a computed signal evaluate untracked instead of throwing. That single change removes the most confusing signal error we hit.
3. Permit static resources under `META-INF/resources` by default in `VaadinSecurityConfigurer`, or log a warning when a request for a static asset is redirected to the login view. Silent unstyled pages are an expensive failure mode.
4. Give `@VaadinSessionScope` a scoped proxy, or document the "resolve after navigation" rule in the browserless testing guide.
5. Add query parameter support to the browserless navigation helpers.
6. When deprecating a family of constants, publish the old to new mapping.
7. The companion line is that a responsive breakpoint belongs to the component's own width, so with an `AppLayout` drawer open the window is wrong by the drawer's width.
