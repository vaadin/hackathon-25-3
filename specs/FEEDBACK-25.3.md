# Feedback for the Vaadin teams: 25.3

Everything found while building this application on 25.3.0-beta1 that a Vaadin team could act on: an API that is missing, one that is awkward, one that is documented but absent, and every place where we had to write a workaround.

This file is part of the specifications on purpose. If this application is ever rebuilt from these specifications, whoever does it should hit none of this by surprise, and should check whether each entry is still true.

**How to add an entry.** One row per finding, in the table that matches its kind. Say what was expected, what happened, what we did instead, and where in this repository the workaround lives. If it is fixed later, do not delete the row: mark it fixed and in which version, because the code that works around it still has to be cleaned up.


## What happens to these

Nothing here has been reported yet. This file is the raw material for two things, and neither is done by writing the row.

**An issue per finding**, in the repository that owns the thing rather than in this one. The finding says which: an API on the server, a binder, a signal, the router, goes to `vaadin/flow`; how a component behaves in the browser goes to `vaadin/web-components`; something documented that does not exist goes to `vaadin/docs`, with the page that promised it; a version or a BOM problem, or a case where nobody can tell which module owns it, goes to `vaadin/platform`. When the answer is genuinely unclear, open it against the platform and let the team move it. One finding, one issue, however many rows it produced here.

An issue needs less prose than a row here and one thing a row does not always carry: **the smallest thing that reproduces it**. Some findings already have one, and those are the ones to open first, because they cost the reader nothing:

- Bind the same property to a `TextField` and to an `EmailField`, and read the error message off each: the first reports the constraint, the second reports nothing.
- Ask `LicenseChecker.isValidLicense` about three products, one of which does not exist, and get the same answer three times.
- Two source roots, the same class in both, and the compiler's answer to what a profile that replaces classes would cost.
- Any application with `@Push`, one page open, one dev loop restart: a stack trace per reconnect attempt, for a race that resolves itself.
- A `Chart` on a page in the dark colour scheme: a white plot area and Highcharts' own palette, until `setStyledMode(true)`.
- A filled AI field marker, and a click on its badge: the popover never opens.
- A form field inside a `Composite`, and the form state the model is given: the field is not in it.
- A `GridAIController` query selecting any SQL `TIME` column: the grid renders empty and the push fails.
- Source tracking on, one live turn, `getFieldSource` on every filled field: all empty.

A finding whose reproduction is "this application, on this branch, on this screen" is not ready to be an issue. Cut it down first or say plainly in the issue that it has not been reduced.

**A hackathon report**, which is the other half. `REPORT.md` carries the numbers and what was built; this file carries what the platform got wrong. The report is written from both, at the end, and it is the only place where "we found fourteen things" is a useful sentence. Here, one row is one thing.

When an issue is opened, put its link at the end of that row. A finding with no link is a finding nobody outside this repository has seen.

## Missing or absent APIs

| Finding | Expected | Actual in 25.3.0-beta1 | What we did | Where |
| --- | --- | --- | --- | --- |
| `bindChildren` does not exist | The 25.3 documentation describes `container.bindChildren(listSignal, factory)` in three separate places, including a shopping cart example and a push example | The method is on no container. It is absent from `flow-server` and from every layout artifact in the release. Only the dev bundle mentions the name | Wrote an adapter that does the same job with `Signal.effect`, rebuilding the child list rather than patching it | `base/signals/Children.java` |
| An application cannot give the AI orchestrator a tool of its own | `withTools(Object...)` on the orchestrator builder, alongside a controller, so an application can add the two or three actions its own screen needs | `withTools` fills an opaque `Object[]` that only a provider which understands annotated objects can read. The tools a provider actually receives as `explicitTools()` come from `controller.getTools()` and nowhere else, so an application that implements `LLMProvider` itself, which the platform documents and which our mock does, never sees them. And `withController` takes exactly one controller, so a surface cannot have both a `FormAIController` and a tool of its own | A record that implements `AIController` by delegating to the platform's controller and appending our `ToolSpec`s to `getTools()`. Twenty lines, and every application that pairs a controller with its own action will write the same twenty | `assistant/Controllers.java` |
| A form field cannot keep an id, so a recorded conversation cannot name one | `setId("phone")` on the field, and that id in the form state the model reads, the way every other Vaadin test and every other integration identifies a component | `FormAIController` mints a fresh random UUID per field on every run and puts the label in the description instead. A real model does not care, because it reads the ids and fills them in the same turn | The mock resolves a cassette's label keys against `get_form_state` before executing the call. It works and it is a workaround for something a component id would have settled | `assistant/MockLLMProvider.java`, `resolveFieldIds` |
| No way to read a computed signal from outside a reactive context without ceremony | `signal.peek()` reads a value without tracking, which is what the error message suggests | `peek()` on a **computed** signal throws, because the computation itself calls `get()` on its dependencies and there is no context. | Components inside a Grid component column are invisible to browserless `find` | `find(Switch.class).all()` after rendering a grid with a component column of switches | Nothing is found: the renderer's components are not part of the searchable tree | Asserted the effect instead, and moved the interaction itself to the browser tier. | `@WithMockUser` is not reliable in a browserless test | Class annotated `@WithMockUser`, navigation to a secured route | Passes when the class runs alone. In a full suite the navigation lands on the login view instead, because the authentication is written before the browserless environment exists and the Vaadin aware security context strategy then reads a different context | A helper that sets the authentication in a `@BeforeEach`, which runs after the environment is up. Browserless should either document this or make `@WithMockUser` work | `TestLogin.java`, used by nine test classes |
| No auto configuration turns a Spring AI `ChatModel` into an `LLMProvider` | `vaadin-ai-core-flow` ships `SpringAILLMProvider`, and `spring-ai-starter-model-openai` publishes a `ChatModel` bean. A Spring Boot application that has both should not need to introduce them to each other | Nothing wires them. Every Spring application writes the same factory, and each one has to discover for itself that a provider instance cannot be shared between two orchestrators, which is the sort of thing that shows up as one screen silently falling back | A three line factory, plus a conditional so that the default build, which has no Spring AI at all, still compiles. A starter that published a prototype scoped `LLMProvider` when a `ChatModel` is present would remove this from every application that uses it | `src/ai/java/.../SpringAIAssistantConfiguration.java` |
| No server side way to build a route's absolute URL | Something like `RouteConfiguration.getAbsoluteUrl(Class, parameters)`, or an absolute form of the URL helpers, for the ordinary case of putting a link to your own application into an email, an invoice or the clipboard | `RouterLink` and `RouteConfiguration.getUrl` produce paths relative to the context root, which is right for navigating and useless for a link that leaves the browser. The only absolute answer, `Page.fetchCurrentURL`, is a round trip to the client and asynchronous, so it cannot be used while building the component that needs the value | Read the scheme, authority and context path off the `VaadinServletRequest` the call arrived on, and fall back to the relative path when there is not one. Every application that emails a link writes this, and each one has to decide for itself what to do behind a reverse proxy | `ordering/ui/CheckoutDoneView.java` |
| Nothing lets an application ask, at runtime, what it is licensed for | A component level `isLicensed()`, or a documented product identifier for `LicenseChecker.isValidLicense`, so an application could adapt rather than guess | `GridPro.class` contains no reference to `com.vaadin.pro.licensechecker` at all. The check lives in the web component, which exposes `static get cvdlName()`, so it runs in the browser during development and in the frontend build for production, and the server never sees it: a `GridPro` constructs happily on a machine with no key. `LicenseChecker.isValidLicense(product, version, buildType)` exists but ignores its product argument. Asking about `vaadin-grid-pro`, about `vaadin-charts` and about a product name that does not exist all return the same answer, which tracks only whether the machine has a valid Pro key | Nothing, deliberately. This build is licensed and Vaadin enforces its own terms, so we removed the probe we had written rather than keep a second, worse copy of a check the platform already does. Recorded because an application that genuinely wanted to adapt at runtime, a demo that must not show a watermark for instance, has no honest way to | By decision, see Licensing in `00-overview.md` |
| `EmailField` swallows the bean validation message and reports nothing | The message the constraint produces, "must be a well-formed email address", the way every other field reports it | The field's own address check wins and its message is empty, so the field turns red and says nothing. Two lines tell the whole story: the same property bound to a `TextField` reads the constraint message, bound to an `EmailField` it reads `""`. Any application with an `EmailField` and bean validation has silent errors on that field, and nothing in the API hints at it | Build the field through a factory that sets `EmailFieldI18n.setPatternErrorMessage`, which restores a message and, unlike the platform's, translates it: Hibernate Validator's default arrives in English whatever language the reader chose | `base/ui/Fields.java`, used by all four views with an email |
| Session scoped Spring beans cannot be injected into a browserless test | `@Autowired CartSignals` in the test class | Fails at injection with "Scope 'vaadin-session' is not active for the current thread", because there is no Vaadin session until the first navigation | Resolve the bean from the `ApplicationContext` after navigating. A scoped proxy on `@VaadinSessionScope`, or a documented test helper, would remove this trap | `ordering/ui/CartBrowserlessTest.java` |

A warning when a generator bean overrides an explicit `@PageTitle`, or a scope on the annotation, would have saved a long hunt | `catalogue/ui/ProductPageTitle.java` |
| Dark mode has two mechanisms and the older one fails silently | `ui.getElement().getThemeList().bind("dark", signal)`, which is what the 25.2 showcase does and what every Lumo era example shows, sets `theme="dark"` on the body. Aura does not read it: it follows the CSS `color-scheme` property, set through `Page.setColorScheme` or `@ColorScheme` | Nothing on screen changes, nothing is logged, and a test that asserts the attribute passes while the feature is dead. We shipped exactly that test and only caught it by clicking the button in a real browser | Use `Page.setColorScheme(ColorScheme.Value.DARK)`, and assert `getColorScheme()` rather than the attribute. A deprecation warning, or a note in the Aura documentation saying the theme attribute does nothing here, would have saved the round trip |
| A `ThemeList` obtained before the theme attribute exists never updates | `element.getThemeList()` returns an object that looks live. If the `theme` attribute is unset at the time, later changes are invisible to that instance | A test asserting on the captured instance passes in one order and fails in another, and the object gives no hint that it is a snapshot | Read `getThemeList()` fresh at every assertion, with a comment explaining why |
| Static CSS imported from a stylesheet is blocked by the default security setup | `@StyleSheet("styles.css")` is served, but the files it `@import`s are ordinary requests. They are not permitted by `VaadinSecurityConfigurer`, so they redirect to the login view, which redirects again, and the browser reports `ERR_TOO_MANY_REDIRECTS` | **The application renders with no styling at all and nothing in the server log says why.** We only found it because a console check flagged four requests to `/login` with a `styles.css` referer | Moved all CSS under `/styles` and permitted that prefix explicitly. A default permit for static resources under `META-INF/resources`, or a warning when a stylesheet request is redirected to the login view, would save the next person an hour |
| A Chart ignores the theme until styled mode is turned on | A `Chart` renders with Highcharts' own palette on a hardcoded white plot area, whatever the colour scheme is. The `--vaadin-charts-*` style properties are inert: the component's own stylesheet guards every one of them behind `:where([styled-mode])`, and Flow does not set it | On Aura, and in dark mode, this is four white rectangles on a dark page, and no error says so. The switch is `configuration.getChart().setStyledMode(true)`, and it is documented only on the Charts styling sub-page: "Basic Use", which is what you read to draw your first chart, does not mention it, and neither does the style properties table that lists the properties it enables. The default is also wrong for 25.3, where Aura and its colour schemes are the default theme and the Java styling API is the older way | Turned styled mode on in the one place every chart is built, with a comment saying why |
| Form field discovery does not walk into a `Composite` | `FormFieldDiscovery` recurses only into children that are `HasComponents`. A `Composite`, which is the platform's own way to write a reusable component, is not one, so every field inside one is invisible to `FormAIController` whatever container it is handed | Our slot picker and order line editor are both `Composite`, so the model was silently offered five fields out of a dozen. Nothing warns: the form state simply comes back short, and the model fills what it was shown and says nothing about the rest | Gave the model those two through tools of our own instead, which turned out better anyway: the bakery can refuse a slot with a reason, and an order line can be added to a list that has no field yet. Discovery should still either walk a `Composite` or say which components it declined to enter | `assistant/PickupSlotTool.java`, `assistant/OrderLineTool.java` |
| A component set as a grid column header is outside the browserless component tree | `column.setHeaderComponent(menuBar)`, then `find(MenuBar.class)` or `find(Checkbox.class)` in a browserless test. Nothing. The same menu found immediately while it was an ordinary child of the view, and moving it into the grid's header made every finder query for it and for its contents return empty | A column chooser, a filter field, a header button: everything an application puts in a grid header becomes untestable through the finder the moment it goes where it belongs. The failure is an empty result, not an error, so a test that looked for a checkbox by label now simply asserts on an empty list | Reach it through the column: `grid.getColumns().stream().filter(...).findFirst().get().getHeaderComponent()`, and walk from there. Worth knowing before writing the test rather than after | `ordering/ui/ColumnVisibilityBrowserlessTest.java` |
| `navigate(String)` rejects a query string | `ui.navigate("track/ORD-1?t=abc")` throws "Base path can not contain query separator" | The natural way to write a link with a token is a single string, and the failure is at runtime, not compile time | Used `navigate(path, QueryParameters.of(...))` |

## The dev loop, measured

Tried on this application, on a JetBrains Runtime, with the numbers in `specs/10-dev-loop.md`. It works, and two things are better than expected:

| Finding | Detail |
| --- | --- |
| A brand new `@Route` class registers without a restart | `redefineClasses(0)`, 0.6 seconds, and the route answers immediately. Nothing in a decade of Flow prepares anybody to expect that, and it is the single most useful thing the loop does |
| A failed compile leaves the app up and serving the last good bytes | Exit 1, the file, line and column, and the page keeps its session. A cart survived a hot swap, a broken edit and the recovery without being rebuilt |
| The instructions are a committed file, not a tool setting | `.agents/skills/vaadin-devloop/SKILL.md` is read by any agent, and `.claude/skills/` is a thin binding to it. Every teammate and every agent on the repository gets the same cycle from `git clone` |

Two rough edges worth passing on:

| Finding | Detail | Suggestion |
| --- | --- | --- |
| One resource in a change set costs the whole batch a restart | A Java edit alone hot swaps in 0.8 seconds. The same edit batched with a translation bundle restarts in 7 seconds, because the classification is decided by the most demanding file. The output does say which file forced it, which is good | Nothing to fix in the loop, but the guidance to "batch the edits" and the cost of batching a resource with Java pull in opposite directions. A line in the skill saying so would save the discovery |
| Every restart with a browser open reports errors that are not errors | `status` after a restarting `apply` says `app log: N error(s)`. | The dev loop's compiler does not use the project's compiler flags | Work through a dev loop session, then run `./mvnw verify` without `clean`. | The Java only limit is invisible until you hit it | Editing the Kotlin view produces no change set entry at all, so `apply` reports success and nothing happened | Name the skipped files: "3 file(s) not compiled: Kotlin is not in the loop" is a one line fix that turns a silent no operation into an explanation |

## A stylesheet added at runtime is not covered by the dev loop's CSS push

`apply` reported `hmr: 1 resource(s) copied, pushed 1 stylesheet(s) in place` for an edit to a stylesheet the application had added with `page.addStyleSheet` at runtime. The file on disk and the copy on the classpath were both new; the browser kept the old one, and the page went on rendering the previous rules.

It is a convincing failure because the report is green and the change is real everywhere except where it matters. We only caught it by reading the rule text back out of `document.styleSheets` and finding the old declaration still there. The confusion lasted a while because switching between a variant that loads the sheet and one that does not re-adds the link, which does fetch the new file, so the change appeared to work whenever a probe happened to switch themes on the way.

Either push the runtime added sheets too, or say `pushed 1 of 2` and name the one that was not pushed. A reload fixes it, but only if you know you need one.

## The container tokens are not interchangeable between themes

`--vaadin-background-container` and `--vaadin-background-container-strong` are in the shared layer, so an application reasonably writes `background: var(--vaadin-background-container)` and expects a sunken surface under either theme. They do not behave the same way:

| Theme | Value |
| --- | --- |
| Lumo | `light-dark(rgba(25,59,103,.05), ...)`, a fixed cold blue grey wash |
| Aura | `color-mix(... from the background colour ...)`, derived from whatever the background actually is |

On a warm background Aura's stays warm and Lumo's reads as a dirty grey white, so the same stylesheet looks deliberate in one theme and broken in the other. It is the one token pair we found where writing against the shared layer is not enough, and it took a side by side comparison to see: each looks plausible on its own.

Deriving Lumo's from `--vaadin-background-color` the way Aura does would make the shared layer mean the same thing in both.

## Missing pieces in the shared token layer

Both themes feed the same `--vaadin-*` properties, which is genuinely good: an application can be written against `--vaadin-background-color`, `--vaadin-text-color`, `--vaadin-border-color`, `--vaadin-radius-*`, `--vaadin-gap-*` and `--vaadin-padding-*` and it follows whichever theme is loaded. This application does exactly that and switching theme at runtime just works.

There is no name for a **raised surface**. `--vaadin-background-color` is the page and `--vaadin-background-container` is a sunken wash, so a card that should sit *above* the page has nothing to ask for. Every application that draws cards therefore invents its own token, and they will all invent a different one.

Setting `--vaadin-background-color` is also **not** how you set the page colour under Aura. Aura recomputes it from its own `--aura-background-color-*` properties rather than passing a value through, so an application that sets the shared token gets a colour three points away from the one the page actually paints. Invisible in isolation, and visible on a sticky bar that has to match the page it sits on. Under Lumo the same assignment lands exactly.

The other gap is the accent. There is no document level `--vaadin-` name for the theme's primary or accent colour: `--vaadin-focus-ring-color` exists only inside component scopes, and everything else is prefixed `--lumo-` or `--aura-`. So an application that wants to paint one of its own elements in "the theme's accent" has to know which theme is loaded, which is the one thing the token layer otherwise saves it from. We left our accent out of the plain variants rather than guess.

## Suggestions

0. Make the old dark mode pattern say something. Setting `theme="dark"` under Aura is a no operation, and it is what every existing example teaches.
1. Ship `bindChildren`, or remove it from the 25.3 documentation until it ships. Right now the first thing a reader tries does not compile.
2. Make `peek()` on a computed signal evaluate untracked instead of throwing. That single change removes the most confusing signal error we hit.
3. Permit static resources under `META-INF/resources` by default in `VaadinSecurityConfigurer`, or log a warning when a request for a static asset is redirected to the login view. Silent unstyled pages are an expensive failure mode.
4. Give `@VaadinSessionScope` a scoped proxy, or document the "resolve after navigation" rule in the browserless testing guide.
5. Add query parameter support to the browserless navigation helpers.
6. When deprecating a family of constants, publish the old to new mapping.
