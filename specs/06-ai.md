# 06 AI

The assistant exists to make one boring job fast: taking a phone order at the counter while a customer talks. Everything else it does is a bonus built on the same wiring.

## Modules and licensing

| Artifact | Licence | What we use from it |
| --- | --- | --- |
| `vaadin-ai-core-flow` | free, needs the `aiComponents` flag | `AIOrchestrator`, `LLMProvider`, `RequestInterceptor`, `ResponseMetadata`, `ToolException`, chat components |
| `vaadin-ai-extensions-flow` | commercial | `FormAIController`, `GridAIController`, `ChartAIController` |

The free half carries the policy layer and the meter. The controllers that write into a form, a grid or a chart are commercial, and this build is licensed for them: see Licensing in `00-overview.md`. Nothing here checks for a licence or substitutes anything when one is missing.

Status: all three controllers are wired. `FormAIController` fills the phone order form with source tracking, field markers and our own popover content. `GridAIController` and `ChartAIController` answer a question by querying, over the guarded read only views described in `features/12-ai.md`.

## Providers

There is one provider and it is the real one. Built with `-Pai` and `OPENAI_API_KEY` present, the application constructs a `SpringAILLMProvider` over the auto configured OpenAI `ChatModel`. Without either, there is no provider and the assistant is off.

Off is a state the application shows, not one it hides. A missing provider logs one warning at startup naming what is disabled, and every assistant surface renders its panel in red. What the panel says is **which of the two switches is off**, because they are different problems with different fixes: a build with no `ai` profile has no provider compiled into it at all, and an `OPENAI_API_KEY` changes nothing there because there is nothing yet to give it to; a build with the profile and no key needs the key exported, not merely set in a shell. Naming both at once sends the reader to the wrong one. `AssistantStatus` carries the reason, and the panel and the log read it. Asking the status for a session when there is none throws rather than returning something.

**Nothing is stubbed and nothing is replayed, and this is a decision, not an omission.** There is no mock provider, no recorded conversation and no parser standing in for a model, because an application that answers a question from a recording is not demonstrating that it can answer questions. What a recording hides is the exact failure worth catching: a panel that has quietly fallen back and looks, to anyone watching a demo, like a working assistant. It also lets a criterion be ticked by a fixture that a real model never produces, which is a lie that survives into a report.

The cost is accepted openly. It means the AI criteria can only be proven by a run that really calls OpenAI, that those runs are tagged `live-ai` and excluded from the default gate, and that a machine with no key proves the half that needs no model and no more. That is a smaller claim, honestly held, and it is the trade this document chooses.

`ai` is a Maven profile, not a Spring one. It adds `spring-ai-starter-model-openai` and compiles `src/ai/java`, which holds the one class in the application that imports Spring AI. Without the profile there is no Spring AI on the classpath, so that class cannot be compiled, let alone loaded, and there is no provider at all.

Nothing implements the live provider by hand: `SpringAILLMProvider` ships inside `vaadin-ai-core-flow`, which is free. `SpringAIAssistantConfiguration` only decides when to build one, on three conditions. The key must be non empty, so building with the profile and no key still boots rather than failing at startup. The Spring profile must not be `test`, because a test that talks to OpenAI is not a test. And the class has to be on the classpath, which the Maven profile settles.

Each orchestrator gets its own provider instance. One instance cannot serve two: the second orchestrator is refused and its screen falls back with nothing said about why. A live provider has a second reason, that it carries the chat memory of whoever is typing into that one screen.

Streaming needs push. The tokens arrive one at a time on a background thread and reach the browser only over a push connection, so `Application` is annotated `@Push`.

Not built: the runtime provider selector. Switching provider still means a restart.

## What a test can prove

The turns are tagged `live-ai` and excluded from every default run, because they really call OpenAI. What the default run proves instead is everything that does not need a model: the tools the model would be given and the rules in them, the query guard, the policy interceptor, and that the assistant says it is off and which switch is off.

A live turn is asserted by shape and not by wording. The model chooses its words, its column names and how much it manages in one turn, so a test that pins those is testing OpenAI's mood. What is a contract: a line is a product the bakery sells in a quantity it allows, a query reads only the three views, a chart has a series and a title.

## The phone order flow, in detail

This is the flagship demo and its specification is exact.

1. The barista pastes a message: "hola, soy Marta Ruiz, quiero dos tartas de zanahoria y seis croissants para el viernes a las cinco, mi telefono es 600 123 456".
2. `FormAIController` discovers the fields of the form, describes them to the model, and lets it read the current values and the available options of every selection field. Discovery walks containers and stops at a `Composite`, so what it finds is the customer identity fields. The order lines and the pickup slot reach the model as tools of ours instead, which is not a workaround so much as the right shape: a list that grows has no field to fill until it has grown, and a slot has to be able to come back refused with a reason.
3. Every write goes through the `Binder`. A rejected value is reported back and the model corrects itself on the next turn, which is why the phone pattern and the quantity range do real work here.
4. Hidden fields stay invisible to the model. Disabled and read only fields are context only. The internal note is marked hidden, so a customer's words never land in a staff only field.
5. Each filled field shows the AI marker. Its popover carries our own content: the source snippet the value came from, and the model's confidence.
6. Source tracking is on. `controller.getFieldSource(field)` gives the confidence level and the extracts, and the extract location highlights the matching span in the pasted text.
7. The barista overrides anything by typing. The marker clears on edit or on revert.

Field rules for the phone order form:

| Field | Rule |
| --- | --- |
| Customer name, phone, email | Filled by the model, always visible with source and confidence |
| Existing customer picker | The model may search but not create. Creating a customer is a human action |
| Product lines | Through `add_order_line`. The model may only choose products that exist, and quantities within range, and a refusal names the catalogue |
| Pickup date and time | Through `propose_pickup_slot`. The model proposes, the slot service validates. A full or closed day is rejected back to the model with the reason and the next free time. It may also ask for the soonest the bakery can serve, because a model that has never seen this calendar cannot name a day |
| Internal note | Hidden from the model |
| Total | Read only, computed, context only |

## Policy layer

`RequestInterceptor` runs before the message list, the history and the request.

| Case | Behaviour |
| --- | --- |
| The message contains a card number shaped string | Masked before it leaves the machine, and a warning is shown |
| The message asks about staff salaries, other customers, or anything off topic | `reject(message)` with a sentence the barista can read |
| An attachment the model cannot read | Converted or rejected with a reason |
| A prompt that would exceed the token budget | Postponed, with the oldest history dropped first |

Tool failures use `ToolException` so the model sees a safe message and can self correct, and the stack trace stays in the log.

## Turn meter

Every turn's `ResponseMetadata` feeds a small panel: token usage, cumulative cost estimate, and the finish reason. A `max_tokens` finish shows the user "the answer was cut off" instead of silently truncating. A turn that fails midway still reports what was observed before the failure.

`setBackgroundExecution(true)` keeps non streaming calls off the UI thread, so the form stays usable while the model thinks. History is restored from the saved messages and attachments when the barista returns to a draft.

## Per turn session context

The orchestrator is given, on every turn: the current route, today's closures, the open slots for the selected location, and the cart or order under edit. The grid and chart controllers additionally carry the state of what they last drew, so a follow up question can refine an answer rather than start again.

## When there is no model

This is about a key and a network, not about a licence. Without the `ai` profile, or with no `OPENAI_API_KEY`:

- Nothing answers. There is no second provider and no parser standing in for one: a free substitute beside a commercial component is ruled out by name in Licensing in `00-overview.md`, and the reason is that a screen with a substitute never has to be honest about which of the two is working.
- Every assistant surface renders its panel in red and says **which switch is off**, the `ai` profile or the key, because they are different problems with different fixes. The startup log says the same thing.
- The phone order form is still a form. A barista fills it by hand, saves it, and a `Channel.PHONE` order lands in the database exactly as it does with a model. That is the offer, and it is what the tests assert with no key.
- Everything that does not need a model still runs and is still asserted: the policy interceptor, the turn meter, the tools and every guardrail on them, and the read only database the query controllers work through.

## Prompt contracts

System prompts live in `src/main/resources/ai/prompts/` as text blocks, one file per surface, versioned like code. The application system prompt outranks the built in controller instructions, which is 25.3 behaviour we rely on to pin the language of the answers to the user's locale.
